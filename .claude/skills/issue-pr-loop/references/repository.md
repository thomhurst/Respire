# Respire

- Every local .NET command uses `scripts/Invoke-AgentDotNet.ps1`, invoked in-process in PowerShell (`& scripts/Invoke-AgentDotNet.ps1 -DotNetArguments @('build')`). Allow the outer timeout at least 30 seconds beyond the guard; exit 124/137 is a validation limit, not permission to raise limits.
- On Windows, retain logs by redirecting an outer `pwsh -NoProfile -File <runner.ps1>` invocation whose runner calls the guard in-process. Redirecting only `& scripts/Invoke-AgentDotNet.ps1 ... *> file.log` can leave an empty file because the guarded native process inherits console handles.
- Run relevant TUnit executable projects under `tests/`, selecting a supported framework and `--treenode-filter` for focus. Set `$env:TUNIT_DISABLE_HTML_REPORTER = 'true'` for local runs, matching CI: the reporter's process-wide ActivityListener changes telemetry-path selection and breaks tests that require no external listener. Prefer `Respire.Tests`/`Respire.Pipeline.Tests` for fast feedback; integration tests require Docker/Testcontainers Redis. Website changes require `npm run build --prefix website`.
- When the full `Respire.Tests` compilation exceeds the guard, use `-p:RespireTestFilter=<source-globs>` for both the guarded build and `run --no-build`; see `website/docs/contributing.md`. This filters compilation before TUnit generation, keeps the real runner/probes, and isolates focused outputs. Keep the 2048 MB limit and diagnostics unchanged; full-suite validation remains in CI.
- Library awaits use `ConfigureAwait(false)`. Never hand-edit `src/Respire/RespireCommands.g.cs`; change `tools/Generate-CommandCatalog.ps1` or an appropriate manual partial/extension. Review/simplification must respect that boundary.
- Preserve networking FIFO response order, buffer reference counts, uninterrupted in-flight writes, and the persistent flush task.
- Never run the full benchmark suite as an agent; benchmark CI owns performance validation. Benchmark workflows run on net10.0 only; do not add a net8.0 benchmark leg or `8.0.x` SDK install to them. Report unavailable Docker validation.
- Aspire samples and the Aspire template smoke test own their AppHost resources. Other integration tests use Testcontainers for ephemeral Redis. Stop only resources started by the current validation; preserve shared lock Redis and peers' resources.
- Claude Code Review posts each review as a PR issue comment from `github-actions[bot]` (marked `<!-- claude-code-review -->`), not as a GitHub review, so it appears only in `issues/<N>/comments`. Treat each one as a full review: its numbered or bold findings and design suggestions are review findings even though there is no thread to resolve. `Assert-PrGreen.ps1` requires a review whose `<!-- REVIEW_HEAD_SHA: <full commit SHA> -->` marker matches the current head. Its latest matching review must carry `REVIEW_VERDICT: CLEAR` or have a later maintainer disposition (write access or higher). That reply must dispose of every finding and include both `<!-- REVIEW_DISPOSITION -->` and the matching `REVIEW_HEAD_SHA` marker. A stale or unstamped review or disposition cannot clear a new head. Only for a PR authored by the Dependabot or Renovate bot, when every Claude review check is explicitly SKIPPED, stale reviews do not require a replacement; any current-head manual review still needs clearance or disposition. Other later comments do not count.
- The required reviewers for `../SKILL.md` § Draft review lifecycle are Claude Code Review and Codex (`chatgpt-codex-connector[bot]`). CodeRabbit and Greptile also comment; dispose of their findings like any other, but their verdicts are not needed to mark a PR ready.
- Claude Code Review reviews drafts on open and on every push; marking a PR ready does not start another review, so the draft review of the current head is the one `Assert-PrGreen.ps1` reads. Its approval is a review for the current `REVIEW_HEAD_SHA` that carries `REVIEW_VERDICT: CLEAR`, or a `REVIEW_DISPOSITION` reply as described above.
- Codex reviews automatically when a PR opens ready, is marked ready, or gets new commits while ready, but never reviews a draft by itself. Findings from the review it runs on promotion are late reviews under step 6 of the lifecycle. While a PR is a draft, request it with `gh pr comment <N> --body-file <file>`, where the body starts with `<!-- issue-pr-loop -->` and a separate `<!-- codex-review:<full head SHA> -->` marker, followed by `@codex review`. A request is pending for 15 minutes after its `createdAt`. When Codex has posted no review, summary update, or thumbs-up for this head by then, the request was dropped; post a fresh one with the same markers. An eyes reaction alone means nothing: Codex often adds one and never reviews. Never tag Codex on a ready PR. Codex's approval is either its `<!-- codex-pull-request-review-summary -->` issue comment whose `codex-review-state:v1` payload has `code_review.commit_sha` equal to the full current head, `status: completed`, `has_any_findings: false` and `has_unresolved_findings: false`, or a thumbs-up from `chatgpt-codex-connector[bot]` on this head's request (check the author through the reactions API). Codex files findings as inline review threads with a priority badge. The summary comment is edited in place, so re-read it on each visit; an older head's summary is not approval.
- Draft CI: `ci.yml`, `modular-pipeline.yml`, `docs.yml`, `agent-guard.yml` and the path-filtered regression workflows skip every PR job on drafts before a runner starts, and run when the PR is marked ready. `converted_to_draft` cancels their in-flight runs through workflow concurrency. `test-full-net8.yml` also skips drafts and runs on readiness when its label is present. Label-triggered benchmark and server-compatibility workflows still run on drafts, because adding their label is an explicit request. The required checks `Build and Test (net10.0)`, `Build and Test (net8.0)` and `modularpipeline` report skipped on a draft; that is not CI evidence for the merge gate.
